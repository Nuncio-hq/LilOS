LilOS — the one document

Read this page, then the code. It holds only what the code can't say: the product, the direction, the map, how work happens, and one line per decision in force pointing at the file with the details. Plans, discussion and history live in GitHub issues.

What LilOS is

A CompanyOS whose employees are AI agents. You hire them, hand them work in threads, watch them work in a real folder, and step in only when they need you. Each thread is one engine session; engines plug in through one generic protocol (Hermes first, never glued in). The engine owns sessions, memory, skills and profiles; LilOS owns only its records: company, projects, channels, messages, tickets, employees. It runs on the Mac (Electron and two background services) and the iPhone (paired over Tailscale).

Stage: prototype. prototype/ is the UI source of truth: a UI change lands in packages/ui (ui-native for mobile) first, Oscar accepts it, then the real app implements it. Mock data is not a contract.

Oscar is the client, not a reviewer. He doesn't write code and rarely reads diffs; he accepts or rejects the product he can try. You own correctness end to end. "Done" means he can try it, with evidence, without reading code. Plain product language. He chats in Vietnamese; the repo is English.

Where it is going

agreed with Oscar 2026-10-14, revised 2026-10-15 and 2026-10-20 · prototypes merged · not decisions yet A slice becomes a decision when it merges; until then the decisions below stay in force.

UX v3: the calm company, threads by project, no DMs (#749, #767)

  • v3 replaces v2 (Oscar, 2026-10-20): Notion-like, colour only for status. People, Work, Goals, live Threads; every row says who holds it, its state, since when, and what it waits on.
  • A thread (one engine session) lives under a project or as a plain chat. DMs go away. An agent picker sits beside the model: a Hermes profile now, other runtimes later through ACP (#111). It reads as a conversation, each turn's work folded in.
  • ⌘K replaces the CEO chat: an answer, or a draft plan, on one keypress. Records open in a side peek (D-#769).
  • Prototype: packages/ui/src/v3 at localhost:5173 (v3's only screen). A thread files under a project by its folder (D-#771); D-#25 and D-#113 say how.

The AI company: a CEO runs the work through tickets (#746)

  • Oscar, the Chairman, talks to one CEO, a position any agent can hold (Paperclip-style). One agent shape: role, reports-to, runtime + model, instructions, memory, skills, connectors. The CEO plans, splits work into tickets, gives each to the right worker, checks the result and reports back. It acts on its own; only risky actions (spending money, sending anything outside, dangerous commands) ask Oscar.
  • Lean tickets, Paperclip-style: goal → ticket → one assignee → status, owned by the relay, driven by gateway tools (ticket_*). An assignee is a LilOS agent or an outside worker the CEO names.
  • Provider-neutral (revised 2026-10-15). Runtimes run threads in a folder: Hermes now; later ones only through one shared ACP mapping, as T3 Code does (contracts first, #764; Codex dropped). Outside always-on bots (Grok Bot, Muse, anything later) are connectors: their own CLI or MCP server, on an agent's sessions. Contracts, relay, harness and UI types never name a provider, wrap its API, or store its credentials. With every connector removed, LilOS still builds and runs; a new provider needs only its CLI or MCP installed. Not: a bot contract with one adapter per provider, or bots listed as runtimes (the 2026-10-14 plan).
  • Prototype: tickets, goals, the CEO and ⌘K plans live in v3 (Work and a ticket's page).
Oscar (Chairman) → the CEO (a position an agent holds) → tickets (ticket_*)
LilOS: projects · threads · tickets · agent gateway
  ├── runtimes (one session per thread): Hermes now · ACP later (#111)
  └── connectors on an agent (CLI or MCP, never wrapped): grokbot · muse · …

How work happens

GitHub issues are the source of truth

  • Nuncio-hq/LilOS via gh. A feature is a parent issue with a product outcome; its sub-issues are vertical slices.
  • Modules: every open issue is a sub-issue of one of five module issues, and its board card carries that Module field. Each module is a slot: swap or empty it and the rest still works: Core (#756: company, projects, threads, agents, tickets, Needs you, lilos_* tools) · Runtimes (#757: Hermes now, others through ACP; models per agent) · Connectors (#758: outside services through CLI or MCP, zero or many) · Mac tools (#759: browser, terminal, Workbench, checkpoints) · Quality (#760: speed, flaky tests, refactors, a11y, iOS upkeep).
  • Labels, only these: agent-ready (criteria + verify plan; anyone may take it; a blocked slice gets it when its blocker merges), later (parked), needs-human (waiting on Oscar).
  • Pick open agent-ready slices with no PR (label:agent-ready -linked:pr); finish a feature's slices before starting another.
  • Take it: remove agent-ready, assign yourself, open a draft PR with Closes #N early; mark it ready when your tier's checks pass (E2E runs only on ready PRs). One slice at a time; stuck → needs-human. One Status comment on the issue (Now / Next / Blocked), edited in place. git commit -s.
  • Done: the merged PR closes the slice; the last slice closes the feature. Then check the card on the "LilOS" board reached Done; if not, move it (gh project item-edit).
  • Work outside the slice → a new issue; don't widen the PR.

Every feature ships its agent tools

  • Agents must be able to use whatever Oscar can: a feature is done only when they can too. Feature issues have an Agent tools section; PRs show one real agent call per new tool.
  • Tools live once in packages/contracts/src/harness/tools.ts as <area>_<action> (seen as lilos_thread_read). A new AppMethod or user-visible action adds its tool or a NOT_AGENT_FACING reason (packages/contracts/src/harness/coverage.ts); a test enforces it.
  • Changing the company is an approval tool (D-#341). Scope comes from the session, never an agent-passed id. Agents use LilOS surfaces, not the engine's browser.

Docs and decisions

  • Two documents: AGENTS.md (short, auto-loaded; CLAUDE.md links to it) and this page. App Review notes (TestFlight beta)

Paste into App Store Connect when a build goes to review; the demo it describes lives in apps/mobile/src/demo.

What the app is. LilOS is the phone companion for LilOS on the Mac: a Slack-style app where the "employees" are AI agents that run on the user's own Mac. The iPhone app is a client of that Mac — it pairs to the Mac app over a QR code and then works against it (read threads, steer agents, approve or deny their tool calls, watch background jobs).

How to review it — no Mac, no account required. Launch the app → Welcome screen → tap "Try the demo" (under "Connect your Mac"). You are inside a scripted, fully offline demo company where every screen works: threads stream replies, approvals can be allowed or denied, plans, subagents, background jobs, settings. A Demo badge floats on every screen; to leave, Settings → Exit demo (or Connect your Mac for the real pairing flow). Exiting leaves nothing on the device. The demo never opens a network connection, so it also works in Airplane Mode.

Privacy: nuncio-hq.github.io/lilos-site/privacy/

What to Test: LilOS is the phone client for AI employees running on your Mac. Tap "Try the demo" to explore every screen offline — no account or Mac needed.
